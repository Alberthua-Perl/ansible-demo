作为资深 Linux 存储性能专家，我来系统梳理 **fio** 输出中关键性能指标的含义。fio 的输出通常分为 **Job 级统计** 和 **全局汇总** 两部分，核心指标如下：

---

### 一、核心吞吐量指标（Throughput）

| 指标 | 全称 | 含义 |
|------|------|------|
| **IOPS** | I/O Operations Per Second | 每秒完成的 I/O 操作数。随机小 I/O 场景（如数据库）的核心指标。<br>• `read: IOPS=xx` / `write: IOPS=xx`：读写分别统计。<br>• `aggrb`：聚合带宽（多 job 时）。 |
| **BW** | Bandwidth | 带宽/吞吐量，通常单位为 **KiB/s**（注意 fio 默认使用二进制单位，1 KiB = 1024 Bytes）。<br>顺序大 I/O 场景（如视频流、备份）的核心指标。 |

**注意**：BW 的 `mean` 是平均值，`stdev` 是标准差。**标准差过大说明性能波动剧烈**，可能受后台 GC、缓存刷盘或资源竞争影响。

---

### 二、延迟指标（Latency）—— 最关键部分

fio 将延迟拆分为三个维度，这是分析存储瓶颈的核心：

| 指标 | 全称 | 含义 |
|------|------|------|
| **slat** | Submission Latency | **提交延迟**。从 fio **创建 I/O 请求** 到 **通过 ioengine 提交给内核/设备** 的时间。<br>反映用户态到内核态的开销、ioengine 效率、系统调用开销。 |
| **clat** | Completion Latency | **完成延迟**。从 I/O **提交给内核/设备** 到 **I/O 完成返回** 的时间。<br>反映真实硬件/内核队列/驱动的处理耗时。**这是大多数场景最关注的延迟**。 |
| **lat** | Total Latency | **总延迟**。从 fio **创建 I/O 请求** 到 **I/O 完成** 的总时间。<br>理论上 `lat ≈ slat + clat`（存在少量统计误差）。|

**重要区别**：
- **同步 I/O**（如 `sync`、`psync`）：调用会阻塞等待完成，所以 `clat` 几乎等于总耗时，`slat` 通常极小。
- **异步 I/O**（如 `libaio`、`io_uring`）：`slat` 只是系统调用开销，`clat` 真正反映硬件能力。

---

### 三、延迟分布（Latency Percentiles）

fio 默认输出或可通过 `lat_percentiles=1` 查看分位值，例如：

```
lat percentiles (usec):
 | 50.00th=[  524], 90.00th=[  876],
 | 95.00th=[ 1020], 99.00th=[ 1464],
 | 99.90th=[ 4832], 99.99th=[16064]
```

| 百分位 | 含义与解读 |
|--------|-----------|
| **50th (P50)** | 中位数。一半 I/O 在此延迟内完成，反映典型用户体验。 |
| **90th/95th (P90/P95)** | 尾延迟起点。若与均值差距大，说明存在间歇性阻塞（如锁竞争、GC）。 |
| **99th (P99)** | 绝大多数请求的延迟上限。SLA 常用指标。 |
| **99.9th+ (P999/P9999)** | 极致尾延迟。若此处突然飙升，通常意味着硬件级问题（如 NAND Flash 的 Read Retry、固件垃圾回收、NAND 擦除）。 |

**性能分析黄金法则**：**看 P99 比看平均值（mean）更有意义**。平均值容易被少量极值拉高或压低，无法反映业务卡顿。

---

### 四、I/O 深度分布（IO Depths）

```
IO depths    : 1=50.0%, 2=30.0%, 4=15.0%, 8=5.0%, 16=0.0%
```

这表示在每个 I/O 提交时刻，队列中正在并发处理的 I/O 数量分布。

- **解读**：如果配置 `iodepth=32`，但此处 90% 的 I/O 深度为 1，说明 **I/O 并发没有打满**，可能是 CPU 瓶颈、同步引擎限制或应用本身串行化。
- **目标**：高 I/O 并发测试（如 NVMe SSD）应看到深度集中在配置值附近。

---

### 五、系统资源消耗

| 指标 | 含义 |
|------|------|
| **usr** / **sys** | 用户态 / 内核态 CPU 占用百分比。`sys` 过高可能说明系统调用开销大、中断密集或驱动效率低。 |
| **ctx** | 上下文切换次数。频繁切换可能降低 I/O 效率。 |
| **majf** / **minf** | 主缺页 / 次缺页中断次数。大量 `minf` 说明频繁分配内存，可能影响延迟稳定性。 |

---

### 六、其他关键指标

| 指标 | 含义 |
|------|------|
| **Runtime** | 实际运行时间（秒）。若与预期的 `runtime` 或 `time_based` 不符，可能 job 提前完成（如设置了 `size` 且跑完了）。 |
| **Total I/O** | 读/写的总数据量（如 `read: io=20480MB`）。可用于验证测试是否覆盖了足够数据量（避免全命中缓存）。 |
| **Err** | 错误计数。非 0 必须排查。 |

---

### 七、混合读写（Mixed）模式特殊输出

当使用 `rw=randrw` 或 `rwmixread=70` 时，fio 会输出：

1. **独立的 read 行** 和 **write 行**：分别展示读和写的 IOPS/BW/Latency。
2. **Combined 统计**：显示聚合后的总 IOPS 和平均总延迟。

**解读要点**：关注读写延迟是否**不对称**。例如写延迟远高于读，可能触发 NAND 的 Program/Erase 或缓存溢出。

---

### 八、专家级解读建议

1. **先看 I/O 深度是否达标**：深度不够，IOPS/BW 数据无意义。
2. **再看延迟分布，而非平均值**：SSD 测试尤其关注 P99 和 P99.9。
3. **区分 slat 和 clat**：如果 `slat` 异常高（如几十微秒以上），排查 ioengine、CPU 调度、系统调用开销，而非怪罪硬盘。
4. **结合 BW 和 IOPS 反推 IO Size**：`BW = IOPS × IOSize`。若发现 BW 很高但 IOPS 不对，检查是否命中了预读或写合并。
5. **注意单位陷阱**：fio 默认延迟单位可能根据数值自动切换（nsec/usec/msec），务必看清表头。
